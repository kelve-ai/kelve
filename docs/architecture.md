# How kelve is built

kelve shows what anything is built on: the person asks their own coding agent to show them a change, a worktree, a repository or some files; the agent opens it in kelve, does kelve's work (finding the way in, reading each file and saying it plainly, tracing ideas down, writing entries), and the reader shows every idea it rests on, down to first principles, with each idea's entry from a shared knowledge graph. This page says how the open-source app is put together.

## The app and the shared graph

This repo is everything that runs on the person's computer: the `kelve` command, the local service, and the reader. It reads from and adds to the shared knowledge graph, a service kelve runs, over the graph's open API (`crates/graph-api`). The graph checks every entry and lesson an agent writes before anyone else reads it, decides how ideas relate, and serves the instructions agents are given and the terms people agree to.

Reading the graph and adding to it go together: both need the person signed in to it (`App::graph_reader`). Each read spends a reading token, signed blind, so the graph knows someone signed in is reading but never who (`graph-api::tokens`). Signed out, kelve works as it does with no graph: the person's agent writes every entry for them alone, and nothing is sent.

## Running kelve

kelve is the `kelve` command, with the web app inside it. Installing it runs `kelve setup`, which connects the person's agent (Claude Code, Codex, Cursor or Gemini) to `kelve mcp`, adds kelve's hook to its settings, and says how much kelve marks. The agent starts `kelve mcp` itself and calls its tools: `open`, `next_job`, `hand_in` and `kept` for kelve's work; `notes` and `note_done` for the notes the person leaves it; `marks` and `set_marks` for what kelve marks; `lessons` and `held` for what other agents learned; and `update`. `open` says the number of what it opened, and `next_job` and `hand_in` take it as `for`, so agents in several tabs each do their own. An agent without MCP uses `kelve job`, `kelve job done`, `kelve kept` and `kelve notes`.

Each asks a running kelve, with the command line's secret; when none answers, `kelve mcp` and `kelve open` start one first, in the background, as `kelve serve --background` in a process group of its own, so closing the terminal leaves it running. Its log goes to `kelve.log` in its data folder. What the agent opens, kelve opens in a new browser tab, signed in with a one-time link, whatever tabs are already open, so it's always in front of the person. Where it can't open a browser, it shows the link where `kelve serve` runs. `kelve stop` asks it to stop. People open kelve at `KELVE_URL`, else `kelve.localhost` on `KELVE_BIND`'s port. The command line reaches it at `KELVE_URL`, else `localhost` on that port, since outside a browser not every system resolves `kelve.localhost`.

Once a day kelve asks GitHub for its newest release (`server::updates`); settings say when there's one, and so does one tool's answer to the agent, once for each version. `kelve update`, or the `update` tool, puts it in place ([releasing](releasing.md)). A newer kelve brings its hook in the agent's settings up to date as it starts.

## The local store

One SQLite file in kelve's data folder for each shared graph kelve has read (`config::store_name`): `kelve.db` for kelve's own graph, `kelve-<host>-<port>.db` for any other, and `kelve-off.db` for none. Ideas, entries, lessons and the graph's sign-in belong to one graph, so changing `KELVE_GRAPH_URL` changes the whole store, and nothing from one graph is shown as another's. In WAL mode, migrated as kelve starts (`crates/store/migrations`), with a copy put aside first when there are migrations to run. It keeps:

What's been read is also kept in the project, in `.kelve/read/`, a file for each text read, by git's blob ID of it, with each passage's marks, the instructions they were read under and every file with that text (`server::read`). It's meant to be committed, so no one in the project reads a file twice.

Beside it, a way in (`server::way`): `.kelve/way.json` holds the project's order to read it in, the rest of its path in parts, a line on what each folder is for, and a print of the project's files, so opened again with files added or gone, the rest of the path is found again. Outside git, or with what's read kept to kelve, it's kept in `kept_way` instead. None of it goes to the shared graph.

Times are milliseconds since 1970, UTC, so they compare as numbers.

## The person's agent does kelve's work

kelve has no model and no key of its own. Everything it needs a model for is a job kept for the person's agent (`server::agent`), each under instructions of its own (`core::instructions`): finding the way in (`way`), the rest of the path (`path`) and what each folder is for (`folders`); reading a file's passages (`read`), checking what was marked and choosing the graph's idea for each (`choose`), and choosing what a folder is built on (`builtOn`); reading a file, a folder or a change plainly (`plainly`, `plainlyFolder`, `plainlyChange`: `server::plainly`, checked by `core::plainly`); tracing how an idea relates (`relate`); writing, fixing or extending an entry (`write`, `fix`, `extend`); doing what a note asks (`note`); and writing what it learned (`lesson`). Each job carries its instructions, served by the shared graph by version (`/v1/instructions/{name}`, falling back to `core::instructions`), sent whole once and then by name; its material, with everything from files or the web fenced as material and never instructions; and the JSON Schema its answer must fit. kelve checks an answer's shape before it takes it, and says what's wrong when it doesn't; one turned away twice is put aside.

What's open goes first, along its way in; tracing comes before writing, so a map is whole before an entry is written from it. Reading anything opened before what's open now is paused until it's opened again, unless an agent was asked for it by its number in the last hour. A job an agent took and didn't answer within ten minutes waits again. kelve can't start the agent and doesn't try: what's kept waits for the next time the person asks it for kelve's work, and the reader says so, with the words to ask with, naming what the tab has open by its number. The agent's list (`server::list`) is the person's view of it: what it's doing now, what's next, what was asked for elsewhere, what's ready, and what's paused.

## The way in

Anything opened with files in it, a folder, some files or a change, gets a way in first (`server::way`): the agent's first job is the order to read it in, each file with why to read it now, and a line on what each folder is for. kelve checks every file is there before it keeps it. Once the way in is read, the agent gives the rest of the path, in parts for understanding, at most 15 files each, eight parts, or twelve above 200 text files. kelve reads only along the way: the way in, each part when the person asks for it, and any file they open. A file opened alone is read at once.

## Marking

When the agent opens something, kelve says how many of its files need reading, and keeps a job for each file on the way that hasn't been read before. Work is never done twice: each passage's marks are kept by a hash of its text, here and in `.kelve/read/`, so a file that changed is read again and only its changed passages go to the agent. Tests are read too, for what they check and how.

1. The engine cuts the file into passages, parsing it once, and finds what in each a mark can point at.
2. The agent reads the passages in one job and marks every idea each rests on that the person's lens asks for (`core::lens`, from `marks.md`, `server::spec`), each with its area and depth, by position: a line and the exact words on it, a run of lines, or a candidate's id. Each names an idea as a reference would title it, never a description of the code, and says in a line how this work uses it (`use`), which the margin shows and which never goes to the graph.
3. Code keeps them to the rules: the words are really there, one mark for each idea (an idea anyone who reads code knows is always basic), none overlapping another (a pattern over lines and an idea used inside it are two), and about one for every 8 lines at most.
4. In a second job the agent checks each mark (a real idea's name, really an instance of it, and something the passage rests on, dropping only everyday words and an idea already marked under another name), and chooses its idea from those offered: the ones the graph has by that name, and kelve's own new ideas with a name like it (the same words, a word more, another spelling, an acronym), which the graph hasn't taken in yet. What was offered is kept with the job, and the answer is read against it. While the graph can't be asked, the check waits for it.
5. The marks are kept against the passage's hash. An unchanged passage is never marked again; one that moves keeps its marks.

Only the ideas' names go to the graph, and a name the graph has exactly doesn't go at all: kelve asks for the bucket of the graph's name index that would hold it, by the first four hex characters of the name's hash, and finds it there, so the graph never learns which name it was after. Only a name the graph lacks is sent, for the nearest spellings. The passage goes only to the person's own agent.

## Plainly

A file, a folder and a change are each read plainly, in one shape, as the agent writes it (`server::plainly`): a file as soon as its reading is handed in, as part of reading it; a folder from its parts, bottom up; a change from its files, last. Each is checked in code (`core::plainly`), and a file's marks are worked out there from its diff, never taken from the agent. It's the person's work, so none of it goes to the shared graph. Code files read plainly unless the person chose to read them as code, overall or by language, in `marks.md`.

## Entries

An idea's entry is taken from the shared graph when it has one. Otherwise it's kept for the agent as soon as the person opens the idea, never ahead. The agent searches the web and reads the pages itself, then writes to one shape (`write@5`), in two layers: a lead of about 80 words that stands alone, then up to five parts (why it exists, how it works around its figure, why it works that way, where it stops, and what else does the job), with at most two folds under each, closed until the reader opens them: a worked example, a common mistake, a look-alike, the precise rule behind a "usually", or more depth. Every block says its part and fold, and keeps its id from one revision to the next. It lists its sources, each at an `https` address it read, and every claim with the words it quotes from each page it cites, and where the entry makes it: a block's id and its words there, kept only when they're there (`core::entry::draft`), so the reader can mark each claim in place while the graph checks it.

kelve builds the entry's blocks and checks its shape in code (`core::entry`), strips secrets once more, and sends it to the graph at once, with the agent's name, model and plan. The person reads it at once, while the graph checks it: each quote against its page, each claim against what it quotes. kelve follows the check (job `entry.follow`) and shows it claim by claim: dotted where a claim isn't checked yet, tinted where one failed, with what its page lacks under it. A claim that fails is kept for the agent to fix, with its words, its quotes and what the graph found with it; if the fix fails too, the entry is dropped. An entry the graph accepts is anyone's to read. It's written from the idea and the web alone, never from anything the person opened.

An entry the graph has changes a block at a time (`core::entry::revise`), and only when someone who adds to the graph opens it (job `entry.refresh`). Found wrong, it's fixed (`fix@4`): only the blocks its problems are in, every other block and claim word for word. Asked for more, by a reader's "Didn't help me understand" or the graph's own grade, a sound entry is extended (`extend@2`, job `entry.revise`): a fold or a block added, nothing touched. Only a poor entry, written before parts, or one mostly wrong, is written again whole. Each goes to the graph against the revision it was written from, as operations on block ids, with the checked claims it leaves out and why. Each claim has a key (`core::entry::claims::key`), so the graph carries a claim it checked on a page that hasn't changed. One the graph turns away is let go, and the graph's entry shown again.

Signing in to the graph is done with GitHub or Google (`api/graph.rs`), and is agreeing to its terms as they are (`/v1/terms`); when the terms change, the person is asked to agree again before anything more is sent. kelve listens on a port of its own for that one sign-in, and opens their browser at the graph with a PKCE challenge. The graph sends them to GitHub or Google and back, then to kelve with a one-time code, which kelve exchanges, with the verifier only it holds, for a key of its own, sealed like every key it keeps. What the agent wrote before is sent then. Reading the graph never carries that key. Settings can delete the account on the graph too: the graph forgets who they are, and kelve forgets the key.

## Relations

How ideas relate is the graph's structure: five kinds (rests on, kind of, answers, alternative to, used with), each with a why. When someone opens an idea the graph has no relations for, kelve keeps a job for the agent to propose them, before the entry is written (`pipeline/relations.rs`, job `entry.relate`), and code holds the shape (`hold`): nothing related to itself, every why one plain sentence, no more of a kind than allowed, a broader category as what it's a kind of. What's proposed is kept to draw the outline at once, goes to the graph with the entry, or on its own, and the entry is written from it. What it rests on is traced the same way, down to first principles. What the graph serves is asked for again at most once an hour; until the graph serves what an idea rests on, what kelve proposed for it is kept, under the new idea's key or the ID the graph gave it.

When the graph answers an ID with the two ideas it became, kelve keeps the two, offers them on the old idea's page, writes nothing more for it, and forgets the marks that led there, so each passage is marked again when its file next opens (`pipeline/splits.rs`).

## The reader

`web/src/reader` is one way to read anything opened. The address holds what it shows (`#/o/<id>?f=<file>&l=<line>&m=<idea to show>&p=<idea>&p=~<idea followed>&t=<tab>&w=all&n=<note, or new>&na=<idea>&np=agent&k=<list or marks>&d=<folder>`), so a reload or Back returns to it.

- **The frame** (`Reader.tsx`): one bar, with the title and line the agent gave, the path through entries, what's ready for you, and the agent's line with how far reading has got; the side panel, with its key at the foot (what the squares mean, and What kelve marks); the work; and what opens beside it, at the right. What's new in a change comes from the server (`reader::change_built_on`), so the side panel, the tree, the gutter and the margin never disagree.
- **The side panel** (`Side.tsx`): In order, the way in and the rest of the path, each step with its square; Files, a tree drawn as it scrolls, each file with one square and each folder with its line; Notes. A change lists every file beside its own without having them read (`/folder?list=true`). There's no Ideas tab: ideas are met in the work, and found with search.
- **Pages read plainly** (`Plainly.tsx`, `FolderPage.tsx`, `ChangePage.tsx`, `PlainRows.tsx`): a file, a folder and a change, each in plain words, each part with the ideas it rests on woven into its sentence, the notes on it, and its code a click away. A change opens on its own page; a folder's name opens its page.
- **The file** (`FileView.tsx`, `code.ts`, `Margin.tsx`, `Ruler.tsx`): code through CodeMirror, read only, for a file read as code. A change's file is one document with the lines it took out where they were, greyed; added lines carry a `+` in a column of their own; each is tinted. It shows what changed, the runs of lines it didn't touch folded by a replacing widget (`code.ts`, `asBefore`); a file not in a change shows whole. The gutter draws a square on each idea's first line, with a stem to a foot on its last; the margin, beside it, each idea's name and the line the agent gave on how the work uses it (`use`); the ruler, where ideas sit in the whole file, and a change's runs. Below 720 pixels the margin's notes go under their lines. Markdown and plain text read as text (`Prose.tsx`), a block a row, from remark's tree, in kelve's own elements: a file's HTML shows as text, its images as their words.
- **Squares** (`Square.tsx`): red for new in the change, grey otherwise; filled until you've read it, hollow once you have; black on a line for a first principle. Read is every idea whose entry was opened, kept in `ideas_read`. On the way in, a step's square is the agent's dial while it works on it, filled once it's ready for you, and hollow once you've read it as the agent left it (`seen.ts`).
- **Entries** (`Panes.tsx`): the idea's question, its entry's blocks (`Entry.tsx`), your notes on it from every project, how it relates as rows, its sources, and Something wrong? and Didn't help me understand. Folds under a part open in place. Following a relation opens its entry beside; the one before narrows and dims. Each view beside the work, an entry, a note, the agent's list or What kelve marks, opens at the right of those already open. A relation followed is kept once and sent to the graph hourly, with nothing about who (`server::follows`). An entry your agent wrote that the graph didn't have asks, there, to be added.
- **Notes** (`NoteParts.tsx`, `NotePage.tsx`, `server::reader`): markdown files with front matter (`core::notes`): with the work in the project's `.kelve/notes/`; just you, and for your agent, in your own notes folder, a folder per project. Written in a box under the lines they're on, drawn there in CodeMirror's block widgets, or as a page beside the work. A note for your agent says `for: agent` and whether it's done, and is a job on its list like the rest; your agent reads those waiting, fenced, with `notes`, and says what it did with `note_done`. kelve's hook, added only with your yes (`core::hook`), runs `kelve moment` as you message your agent, which says when notes wait.
- **Your agent's list** (`ListPane.tsx`): what it's doing now, what's next, what's ready and what's paused, with Do next and Take off.
- **Search** (`Search.tsx`), on ⌘K or Ctrl K: what's newly written for you in the last day first (`/api/opened/{id}/written`), then ideas here, then from the shared graph, then lessons about the work, files, lines that say the words and notes, then what you can do. Before you type, this work's ideas, those in the most files first, and its lessons.
- **The first run, settings and adding** (`screens/`): connect your agent, with the example beside it (`Example.tsx`, answered from `src/example/example.json` with no server); settings in seven pages; and adding to the shared graph, where you sign in and see the terms.

## Lessons

What people's agents learned using an idea, kept in the shared graph beside its entry. One shape for any work, checked in code before it leaves (`core::lesson`).

- **Given at the moment it helps.** kelve's hook, `kelve moment --agent
  <agent> --on <event>` (`cli::moment`), runs on each agent's own events,
  for eleven agents (`core::hook` reads each one's event as kelve's moment and answers it its own way; `server::hooks` puts it in and takes it out). As the agent reads or edits a file, runs a command, or something fails, kelve gives a lesson only if it fits the work and matters there (`core::matching`): nothing in its "holds when" fails against the work's context (`engine::context`: lockfiles, citation style, language), and its cues are in what was written or read, its codes and words match the problem's fingerprint, or a command runs a tool the usual way the lesson replaces. Two at a moment, ten a session, never one twice; once a lesson has been given a hundred times across everyone, one in twenty that fits is held back, to measure it. kelve, not the author, writes how far each is confirmed. Agents ask too, with the `lessons` tool, by the error or by the ideas they use.
- **Fetched like relations.** The lessons about the ideas in what kelve reads, the libraries its files import and the tools the agent runs (`cargo`, `pytest`) are fetched by the ideas' IDs and kept a day (`store::lessons`). A library or tool is found in the graph by its name alone, through the name index's buckets. A folder the hook meets the agent in that the person never opened is walked once for what its files import, with nothing read or marked. Matching a file or a problem to them happens here.
- **What showed it held.** Each lesson given is kept with what came of it, by the strongest sign: the same error came back, or it didn't and the same command passed, the commit has the work done the lesson's way, or the agent said, with `held`. Hourly, only the lesson, the outcome and the sign go to the graph, as the account, so a project counts once.
- **Written when it was hard won.** As a turn ends (Claude Code's and Qoder's `Stop`; for other agents, the person's next message), what failed since kelve last asked is one stretch. When it was hard (two failing runs or more, two different errors, or five minutes) and the agent got past it, kelve keeps a `lesson.write` job, with the lessons already known first, so the easy answer is "that's this one". When the agent replaces more than a couple of lines of its own earlier work, with its edit tool or through its shell, and the second way stands, that's a job too: a better way. What the agent writes waits a day, listed in settings with Stop, then goes as `lesson.send`.
- **In the reader**, the least: a line on a change saying what the graph gave, "Used a lesson" on a part, the lesson in the entry pane, lessons in search, a few under an entry, and what the agent learned, leaving later, with Stop (`Lessons.tsx`).

## Work shown before it's merged

When the agent is about to merge work kelve hasn't shown the person, kelve's hook says to show it in kelve first, once for each commit (`server::handoff`, `core::hook::merging`). Merging again goes ahead.

## When something goes wrong

kelve sends no report of a problem anywhere. When it panics, or its page meets an error, it keeps a short report in `problems/` beside its data (`server::problems`), at most 20, the oldest going first. Each is tidied first (`core::problems`): secrets stripped as everywhere, paths on the person's computer taken out (kelve's own source files and other crates' stay, by where they are in the code), and a backtrace kept as function names only. Settings shows each report exactly as it's kept, with a link that starts an issue on kelve's repository filled in with it, which the person reads again on GitHub before posting, or not; or they forget it. The start page says when there's one to look at.

## The weekly count

kelve counts a few things a day (`server::counts`): what's opened, by kind; entries read, and how many came from the shared graph; links followed, and how many led to an entry already written; notes written, by where they're kept; jobs the agent did; files read plainly; lessons asked for, written, given, and how they held; and the day an agent first said hello. Only numbers are kept: an idea's key is kept for a fortnight so a page asked for again isn't counted again, then forgotten. kelve's first screen asks once whether to share them. If the person says yes, kelve makes the install a random ID, 128 bits, deleted when they stop, and sends the shared graph last week's count once a week (`POST /v1/counts`): the week's counts and each day's, kelve's version, the platform and that ID, with no account, no key and no reading token, so the graph can't tie it to anyone. `DO_NOT_TRACK` or `KELVE_TELEMETRY=off` keeps it from going, whatever was chosen. Settings shows this week's exactly as it would go, and every week sent, as sent. The graph forwards each to PostHog, from its own server.

## Signing in

kelve makes a one-time link that signs a browser in, and opens it, or shows it where `kelve serve` runs. `kelve open` asks for a new one. The command line shares a secret with kelve, in a file only its owner can read; with it, the command line can ask for a link, never have one.

## The tests

`cargo test` runs everything, with stores made in memory or in a temporary folder, and a stand-in for the agent and for the graph. It also writes the web app's types (`web/src/api/gen`) from `core::views`, and the graph's OpenAPI document. `web/e2e` starts kelve beside the stand-in graph, with a stand-in agent that calls kelve as `kelve mcp` does (`web/e2e/agent.ts`), and tests it in a browser, as people use it (`web/e2e/tests`); `example.spec.ts` does so on the example, with the example's own agent. `web/e2e/looks` takes a screenshot of every state of every screen (`src/example/states.ts`), drawn from the example, and compares each with the one committed, in Playwright's Linux image.
